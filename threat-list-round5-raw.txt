--- FINDING #1 ---
Severity: HIGH
Category: Race Condition — Nonce upsert / unique partial index interaction
File: backend/src/models/Nonce.ts, line 30-37
File: backend/src/routes/auth.ts, line 83-87

Description:
The Nonce model has a unique partial index on `{ address: 1 }` with
`partialFilterExpression: { used: false }`. The /nonce route uses
`findOneAndUpdate({ address, used: false }, { $set: { nonce, created_at } }, { upsert: true })`.

This is CORRECT in theory — the partial unique index prevents two concurrent
/nonce calls from creating two unused nonces for the same address. However,
there is a subtle interaction with MongoDB's `findOneAndUpdate` + `upsert`:

When `findOneAndUpdate` with `upsert: true` fails due to a duplicate key error
(E11000), the operation does NOT retry. The error propagates to the catch block
which returns a generic 500 "Failed to create nonce". In a race between two
concurrent /nonce calls:
  - Call A: findOneAndUpdate → finds nothing → tries upsert insert → SUCCEEDS
  - Call B: findOneAndUpdate → finds nothing → tries upsert insert → E11000 duplicate key

Call B's user gets a 500 error with no nonce, and cannot authenticate.

The `findOneAndUpdate` with `upsert` does NOT atomically handle the case where
the filter matches an existing document AND the upsert insert would collide.
MongoDB's atomicity guarantee for findOneAndUpdate is: the find and the
modification (update or insert) are atomic as a single operation. The unique
constraint check happens during the insert phase of upsert. If two operations
both attempt to insert (because neither found a matching doc), one will fail.

This is a HIGH-severity issue because it can cause authentication failures for
legitimate users during normal concurrent use (e.g., two browser tabs both
loading and triggering /nonce simultaneously).

Fix: Either:
  (a) Use `findOneAndUpdate` without `upsert`, and if no doc is found, use
      `insertOne` wrapped in a retry-on-duplicate-key loop, OR
  (b) Use `updateOne({ address, used: false }, { $set: ... }, { upsert: true })`
      which is idempotent — if the insert fails due to duplicate key, the
      operation is safe to retry as an update, OR
  (c) Catch E11000 specifically and retry as an update (not insert).

--- FINDING #2 ---
Severity: HIGH
Category: Input Validation — No validation of objectId parameter in staking routes
File: backend/src/routes/staking.ts, line 332-335
File: backend/src/services/sui.ts, line 136-137

Description:
The route `GET /api/staking/nft/:objectId` accepts `objectId` from the URL
params and passes it directly to `rpcCall('sui_getObject', [objectId, ...])`.
There is NO validation of the objectId format before it reaches the RPC.

An attacker can:
  - Send arbitrary strings that cause RPC errors, wasting RPC quota
  - Potentially inject JSON-RPC parameters if the objectId contains special
    characters (though unlikely with the current JSON.stringify path)

The same issue applies to `GET /api/image/:objectId` in image.ts (line 57),
where the objectId is hashed with MD5 and used in filesystem paths — though
that's lower risk since it's hashed.

At minimum, the objectId should be validated as a valid Sui object ID (hex
string of appropriate length, typically 66 chars with 0x prefix for addresses,
or 64-char hex without prefix for object IDs).

--- FINDING #3 ---
Severity: HIGH
Category: Business Logic — Point calculation uses stale holding multiplier for ranking
File: backend/src/routes/ranking.ts, line 117-127

Description:
In the ranking endpoint, for each user, the holding multiplier is computed as:
  `const nftCount = activeStakes.length;`
  `const multiplier = getHoldingMultiplier(nftCount);`

Then this SINGLE multiplier is used for ALL stakes of that user (active AND paused):
  `const { points, durationDays } = computePoints(stake, multiplier, now);`

However, for paused stakes, `computePoints` correctly returns only `locked_points`
(since `status !== 'active'`). The multiplier passed in is irrelevant for paused
stakes in the current implementation. BUT: the `nftCount` here is based on
`activeStakes.length` from the DB, NOT from the on-chain owned count. If the DB
is stale (user hasn't synced recently), the multiplier will be wrong.

More critically: the multiplier used for ranking may differ from the actual
session_multiplier that was frozen when points were earned. For active stakes,
`computePoints` uses `stake.session_multiplier` (the frozen value), not the
passed `holdingMultiplier`. So the ranking's `multiplier` field in the response
is misleading — it shows the CURRENT multiplier, not what was actually used to
compute points.

This is a display inconsistency. The actual point totals are correct (they use
session_multiplier), but the displayed multiplier field is wrong.

--- FINDING #4 ---
Severity: HIGH
Category: Resource Exhaustion — Unbounded in-memory Map growth (no TTL cleanup)
File: backend/src/routes/staking.ts, line 19
File: backend/src/routes/visitor.ts, line 7
File: backend/src/routes/auth.ts, line 17
File: backend/src/routes/image.ts, line 31
File: backend/src/routes/ranking.ts, line 14
File: backend/src/routes/image.ts, line 23

Description:
Multiple in-memory Maps accumulate entries with only periodic cleanup triggered
by size thresholds:

1. `syncRateLimitMap` (staking.ts:19) — cleaned every 100 entries. If an attacker
   rotates through many unique IPs, each IP gets one entry and the map grows
   unboundedly between cleanup cycles. With 100k unique IPs, the map holds 100k
   entries before any cleanup triggers.

2. `visitorRateLimit` (visitor.ts:7) — cleaned only when size > 10000. Same issue.

3. `authLastSeen` (auth.ts:17) — cleaned every 100 entries. Same issue.

4. `imageLastSeen` (image.ts:31) — cleaned every 500 entries. Same issue.

5. `rankingLastSeen` (ranking.ts:14) — cleaned every 200 entries. Same issue.

6. `filenameCache` (image.ts:23) — NEVER cleaned. Grows unboundedly with every
   unique objectId ever requested. This is a permanent memory leak. If the image
   proxy serves 100k unique NFTs over the process lifetime, this Map holds 100k
   entries forever.

The periodic-cleanup-on-size-threshold pattern is fundamentally flawed: if an
attacker sends requests from many unique IPs at a rate just below the throttle
threshold, entries accumulate faster than they're cleaned. A single attacker
with access to an IPv6 /64 can generate 18 quintillion unique IPs.

Fix: Use a proper TTL-based cache (e.g., `node-cache` or a `setInterval`-based
cleanup that runs on a timer, not a size threshold). For `filenameCache`, add
an LRU eviction policy with a max size.

--- FINDING #5 ---
Severity: MEDIUM
Category: Race Condition — Background sync and user sync can interleave on the same address
File: backend/src/services/backgroundSync.ts, line 41-153
File: backend/src/routes/staking.ts, line 43-151

Description:
Both `backgroundSync.syncAllAddresses()` and the user-triggered
`syncStakesForAddress()` can operate on the same address concurrently.

Scenario:
1. Background sync starts processing address A
2. User triggers POST /api/staking/sync for address A
3. Both read `existingStakes` from DB
4. Both modify stakes and call `.save()`
5. The second `.save()` overwrites changes from the first

This can cause:
- Lost point accrual: background sync pauses an NFT and locks points, then
  user sync overwrites with stale data
- Duplicate session starts: both set `current_session_start` to `nowIso`
- Lost multiplier updates: one sync updates `session_multiplier`, the other
  overwrites it

The background sync has `isSyncing` guard but it's a single boolean — it
prevents TWO background syncs from running, but does NOT prevent a user sync
from running concurrently with a background sync.

Fix: Per-address locking (e.g., a `Map<string, Promise>` of in-flight syncs)
or use MongoDB's `findOneAndUpdate` with optimistic concurrency control (a
version field).

--- FINDING #6 ---
Severity: MEDIUM
Category: Error Handling — Information disclosure via error messages
File: backend/src/routes/image.ts, line 129-136

Description:
When an image download fails, the error response includes the HTTP status code:
  `res.status(502).json({ detail: 'Failed to fetch image: ${imageRes.status}' });`

While HTTP status codes alone are not highly sensitive, combined with timing
and the SSRF guard's behavior, an attacker could use this to probe internal
services:
1. Attacker sets NFT image_url to `http://internal-service:8080/`
2. SSRF guard blocks it (private IP)
3. Attacker gets a different error than for a valid external URL

This is a minor information leak — the attacker can distinguish between
"blocked by SSRF guard", "connection refused", "HTTP 404", "HTTP 200", etc.
This enables internal port scanning albeit with limited resolution.

The `assertSafeImageUrl` in ssrfGuard.ts correctly blocks private IPs, so the
practical risk is low, but the error differentiation is still a minor leak.

--- FINDING #9 ---
Severity: MEDIUM
Category: Input Validation — image.ts disk probe: existsSync in a loop, path traversal risk
File: backend/src/routes/image.ts, line 73-82

Description:
The disk cache probe iterates through extensions and checks `fs.existsSync()`:

  const hash = crypto.createHash('md5').update(objectId).digest('hex');
  const exts = ['png', 'jpg', 'jpeg', 'gif', 'webp', 'avif'];
  for (const ext of exts) {
    const candidate = `${hash}.${ext}`;
    if (fs.existsSync(path.join(CACHE_DIR, candidate))) { ... }
  }

Issues:
1. `objectId` is hashed with MD5 before use in filenames, so path traversal
   via `../` in objectId is not possible. The hash output is always hex. SAFE.

2. `existsSync` is synchronous and blocks the event loop. With 6 extensions
   to check per request, this is negligible. However, if the CACHE_DIR is on
   a slow network filesystem (NFS, EFS), these 6 sync stat calls could block
   for hundreds of milliseconds each. In practice, the cache is local disk.

3. The `filenameCache` in-memory Map (line 23) should make the disk probe
   rare — once an image is cached in memory, the existsSync loop is skipped.
   This is correctly implemented.

4. EDGE CASE: If two different objectIds produce the same MD5 hash (collision),
   they would share a cache file. MD5 collisions are computationally feasible
   but extremely unlikely in this context. An attacker would need to create a
   Sui NFT with a specific objectId that MD5-collides with another. Not
   practically exploitable.

5. The probe checks all extensions in order and returns the first match. If
   both `hash.png` and `hash.jpg` exist (unlikely but possible if the same
   objectId was cached with different content types across restarts), only
   the first match (png) is served. This could serve a stale/wrong image.
   VERY LOW risk since the same objectId should always have the same image.

Overall: The disk probe logic is correct and safe. The use of `existsSync` is
acceptable given the small fixed loop size and the in-memory cache bypass.

--- FINDING #10 ---
Severity: MEDIUM
Category: Resource Exhaustion — download-images.ts: readdirSync on every downloadImage call
File: backend/src/scripts/download-images.ts, line 43

Description:
In `downloadImage()`, the cache check uses:
  `const existing = fs.readdirSync(CACHE_DIR).filter(f => f.startsWith(hash));`

This is O(n) where n is the number of files in the cache directory. With 10,000+
cached images, this blocks the event loop on every call. The script processes
NFTs sequentially, so each one calls this.

For a one-shot script this is acceptable (runs once). But in `--watch` mode,
the script runs every 30 minutes. If the cache grows to 100k files, each
`readdirSync` becomes expensive.

Fix: Use the same hash+extension probe pattern as image.ts (check specific
filenames with existsSync instead of scanning the whole directory).

--- FINDING #14 ---
Severity: LOW
Category: Resource Exhaustion — download-images.ts watch mode: seenAcrossCycles cleared at 100k
File: backend/src/scripts/download-images.ts, line 226-229

Description:
In watch mode, `seenAcrossCycles` tracks already-downloaded NFT IDs. When it
exceeds 100,000 entries, it's completely cleared:
  `seenAcrossCycles.clear();`

This means after 100k unique NFTs, ALL previously downloaded NFTs will be
re-fetched from chain (RPC calls) and re-checked against disk. This is a
thundering-herd reset — the next watch cycle after clearing will re-scan
everything.

For a collection with <100k NFTs this is fine. For larger collections, the
periodic full re-scan could cause RPC quota exhaustion.

The disk cache (`existsSync` per hash+ext in downloadImage) prevents actual
re-downloads, but the RPC calls to `getNftMetadata()` still happen.

Fix: Use an LRU eviction policy instead of clearing everything, or simply
trust the disk cache and don't track seenAcrossCycles at all (just check disk).

--- FINDING #16 ---
Severity: LOW
Category: Race Condition — TTL index + unique partial index compatibility
File: backend/src/models/Nonce.ts, line 21, 30-37

Description:
The Nonce collection has three indexes:
1. `{ created_at: 1 }` with `expireAfterSeconds: NONCE_EXPIRY_SECONDS + 60` (TTL)
2. `{ address: 1, used: 1 }` (standard)
3. `{ address: 1 }` unique partial `{ used: false }`

MongoDB allows TTL indexes and unique indexes to coexist on the same collection
without conflict. The TTL index operates on `created_at` while the unique index
operates on `address`. They don't interfere.

However, there's a theoretical edge case:
- Nonce A is created at time T, expires at T + 360 (300 + 60)
- Nonce A is used (set used=true) at time T + 100
- The TTL index will delete Nonce A at T + 360 (based on created_at, not
  updated_at)
- Nonce B can be created for the same address at T + 100 (because Nonce A is
  now used=true, so it doesn't violate the unique partial index)

This is CORRECT behavior. The TTL cleanup is based on `created_at`, which is
intentional — it guarantees cleanup even if the nonce is never used.

No conflict between these indexes. CONFIRMED SAFE.

--- FINDING #21 ---
Severity: LOW
Category: SSRF — ssrfGuard.ts: IPv6 private range check is incomplete
File: backend/src/services/ssrfGuard.ts, line 22-40

Description:
The `isPrivateIp` function checks IPv6 private ranges:
  `v.startsWith('fe80:') || v.startsWith('fc') || v.startsWith('fd')`

This covers link-local (fe80::/10) and unique local (fc00::/7). However, it
does NOT check:
- `::ffff:0:0` to `::ffff:0:ffff` (IPv4-mapped IPv6, partially handled via

- `64:ff9b::/96` (NAT64 well-known prefix)
- `100::/64` (discard prefix)
- `2001:db8::/32` (documentation prefix)

These are low-risk omissions. The most important check (::ffff: for IPv4-mapped)
is handled. NAT64 could theoretically be used to route to internal IPv4
addresses, but this requires a NAT64 gateway on the network path — unlikely in
a typical cloud deployment.
